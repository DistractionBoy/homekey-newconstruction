## [LRN-20260912-001] best_practice

**Logged**: 2026-09-12T21:39:38Z
**Priority**: high
**Status**: pending
**Area**: frontend

### Summary
Patch-at-every-call-site instead of fixing the shared wrapper caused a 49-occurrence fix across 15+ files that was still incomplete.

### Details
The `@base-ui/react` `<Button>` in `components/ui/button.tsx` defaults to rendering a native
`<button>`. When used as a link via `render={<Link/.../>}`, this nests interactive elements
(button-in-a / `<a>` inside `<button>`) — invalid HTML that fails a11y checks and drags down the
Lighthouse score. Commits `6537218` then `97858ab` added `nativeButton={false}` to **49 call sites
across 15+ files** in two passes, and the second pass was still needed because the first didn't
cover everything. The `/es/` Spanish pages duplicate the English CTA blocks, so the same fix had to
be re-applied a second time in Spanish translations.

### Suggested Action
Fix at the source, not the call sites:
- Done: `components/ui/button.tsx` now defaults `nativeButton={false}` (correct default when `<Button>`
  is used with `render={<Link/>}`).
- `components/ui/carousel.tsx` prev/next buttons use `onClick` and therefore need a real native
  button — they now explicitly pass `nativeButton`. If you add more `onClick`/`type="submit"`
  `<Button>` usages, pass `nativeButton` on them too.
- Consider a dedicated `<ButtonLink render={<Link/>}>` component so link-CTAs can't accidentally
  regress to a nested-interactive button.
- The 49 remaining `nativeButton={false}` props are now redundant (harmless). They were left in place
  to avoid a large, risky mass-delete that can't be build-verified (see ERR-20260912-002). A cleanup
  pass to delete them is safe once a build/test run confirms behavior.

## [LRN-20260912-002] best_practice

**Logged**: 2026-09-12T21:39:38Z
**Priority**: high
**Status**: pending
**Area**: frontend

### Summary
Sitemap is generated by `next-sitemap` at build time, but a stale hand-edited `public/sitemap.xml`
is also tracked in git — the two drift apart and cause "broken links" churn.

### Details
`package.json` runs `postbuild: "next-sitemap"` (config in `next-sitemap.config.js`, which reads the
live route tree). Yet `public/sitemap.xml` is also version-controlled and was hand-edited in
`1819183` ("fix some broken links"), out of sync with actual routes (it referenced `/blog`,
`/schedule` pages that didn't exist yet). A generated artifact that is hand-edited and committed is
the classic source of repeated, throwaway fix commits.

### Suggested Action
- Treat `public/sitemap.xml` (and any `public/robots.txt`) as a generated build artifact: stop
  editing it by hand and, ideally, `gitignore` the generated output so the build output is the single
  source of truth.
- When adding/removing routes, create the page (route) *before* anything links to it; do not add a
  link/sitemap entry for a route that doesn't exist yet.
- Confirm with the team whether the checked-in `public/sitemap.xml` is intentional (some deploy
  pipelines serve it statically without running `postbuild`); if so, generate + commit it from the
  build step rather than editing manually.

## [LRN-20260912-003] best_practice

**Logged**: 2026-09-12T21:39:38Z
**Priority**: medium
**Status**: pending
**Area**: infra

### Summary
Lighthouse CI was fixed in 4 hedged commits ("pass hopefully"); set the foundational items in one pass.

### Details
Commits `446264d` → `cf5111a` → `628d9cd` → `97858ab` each nudged Lighthouse closer (`446264d`
edited `lighthouserc.json`, `cf5111a` deleted it and rewrote the GH workflow with `wait-on`,
`628d9cd` added `metadataBase`, `97858ab` bumped two CSS values `gap-3`→`gap-4` and slider tap
targets `h-2`→`h-6`). Each was a separate guess rather than a planned, complete fix.

### Suggested Action
- Set `metadataBase` in `app/layout.tsx` from the start (already added in `628d9cd` — keep it; it
  underpins absolute URLs/og tags).
- Give interactive/scroll controls a min size up front (h-9 / ~44px tap targets) rather than chasing
  Lighthouse's "tap targets appropriately sized" / control-size warnings after the fact.
- When adding Lighthouse CI, get the config correct in one pass (workflow + `wait-on` + assertions)
  instead of toggling `lighthouserc.json`; commit messages like "hopefully"/"try fixing" are a signal
  the fix is unverified — verify locally with `lhci` before pushing.
